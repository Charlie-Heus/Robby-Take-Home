  The assignment

  You're building a minimum version of a follow-up engine for open home-service
  quotes. It needs to:

  1. Ingest the events.
  2. Rank who to contact for a given "now", with a reason for each, and list
     other signals you'd use.
  3. Draft the message.
  4. Draft → approve → send, with three guardrails:
     - no messaging the same customer twice within a cooldown window
     - no messages about accepted or dismissed quotes
     - re-running the engine or retrying a failed send never double-sends
  5. Run on localhost.

  The deliverables are the code, tests for the risky parts (not full coverage),
  this conversation (use /export), and a README. The README covers how to run
  it, your follow-up policy and why, two paragraphs with no code on running this
  for 50 shops, and what you'd build next. The time limit is 3 hours. They
  grade on handling messy data, the guardrails, how quote and message state is
  modelled, and your judgment calls. They don't grade the UI or framework
  choice, and you need to be able to defend every choice.

  The data

  - quotes.json: 30 quotes: 27 open, 2 accepted (Q-1004, Q-1017), 1 dismissed
    (Q-1009). Amounts run from $420 to $22,000. There are 5 techs.
  - events.jsonl: 88 lines, all valid JSON, all timestamps in the same UTC
    format, and every event points to a known quote. The latest event is
    2026-08-16 16:00Z, so a sensible default "now" is around Aug 17, not today.

  Problems in the data (these are what they're testing)

  1. Duplicates: 6 events appear twice with the same event_id and identical
     content. Removing duplicates by event_id is enough; no two different ids
     share the same content.
  2. Out of order: 41 neighbouring pairs are out of time order. State has to
     come from event timestamps, not file order. Late events also have to be
     handled safely after the fact.
  3. An event type the PDF doesn't mention: quote_sent (32 of them). Each one
     matches its quote's created_at, apart from the two Q-1000 and Q-1014 events
     that are just duplicates. The general point is that unknown event types
     should be kept but not acted on, rather than crashing the import.
  4. Two quotes, one customer: Karen Nguyen has Q-1003 and Q-1025 on the same
     phone, +19175552003. The cooldown has to be per phone number, not per
     quote. Otherwise she could get two texts in one day.
  5. last_contact_at disagrees with the events in both directions:
     - Q-1002, Q-1005, Q-1012, Q-1019 and Q-1027 have message_sent events later
       than the quote's last_contact_at. Q-1005 and Q-1012 even show null.
     - Q-1003, Q-1013 and Q-1020 have a last_contact_at with no matching
       message_sent event.
     - So the real last contact should be the latest of the snapshot value and
       the events, and the snapshot alone can't be trusted.
  6. Status and events conflict:
     - Q-1017 is accepted but has no quote_accepted event.
     - Q-1004 and Q-1009 get views after being accepted or dismissed.
     - A closed status should be final: later views don't reopen a quote.
  7. Strong signals worth using:
     - Q-1012 ($18k) was viewed 3 times on Aug 13 and nobody has replied since
       the Aug 7 text.
     - Q-1000 was viewed 3 times and has never been contacted.
     - Q-1015 and Q-1016 have customer replies with no answer from the shop.
       That's arguably the top priority, and it calls for a human to reply
       rather than an automated nudge.
     - Q-1010, Q-1021 and Q-1024 are big quotes with no activity at all.

⏺ The schema is in place: the three tables are in followup/schema.sql, and
  followup/db.py creates them. It's plain Python with no dependencies. To create
  the database, run:

  python3 -m followup.db

  That writes followup.db in the project folder, which I've added to .gitignore.
  Running it again is safe.

  The tables

  - quotes: the seed data as given. status must be open, accepted or dismissed.
    last_contact_at is kept but treated as an unreliable snapshot; the real
    value will be calculated from events. There's an index on phone number
    because the cooldown is per customer.
  - events:
    - Key: event_id is the primary key, so a duplicate event is simply ignored
      when ingesting.
    - Lenient on purpose: any event type is accepted (so quote_sent is kept),
      and events can reference quotes that aren't loaded yet.
    - Columns: a source column (webhook or engine) tells customer events apart
      from our own message_sent writes, and raw keeps the original JSON.
  - outbox:
    - Status: must be draft, approved, sending, sent or failed.
    - Columns: idempotency_key must be unique. customer_phone is copied onto the
      row when the draft is made. There are also attempts, last_error and
      provider_message_id for retries.
    - One I added: a rule in the database allowing only one draft, approved or
      sending message per phone number at a time. Karen's two quotes can't both
      have messages waiting.

  Checked

  I tried inserting bad rows on purpose, and the database rejected each one: a
  repeated idempotency key, a second waiting message for the same phone, an
  invalid status, and an outbox row for a quote that doesn't exist. A sent
  message alongside a new draft is still allowed, which is correct. I also added
  these schema decisions to notes.md.

  Still to decide

  - How the idempotency key is built: I've left this for the policy step. My
    suggestion is quote, reason and the event that triggered it, so the same
    situation can never produce two drafts.
  - Status changes: the allowed moves (draft → approved → sending → sent, and
    failed → retry) aren't enforced by the database yet. They'll be enforced in
    code in the send step.

  -- All timestamps are ISO-8601 UTC strings ("2026-08-16T16:00:00Z"), so they
  sort lexically.

  -- Snapshot of quotes as imported. Derived state (real last contact, last
  view,
  -- unanswered reply) is computed from events, not stored here.
  CREATE TABLE IF NOT EXISTS quotes (
      id              TEXT PRIMARY KEY,
      customer_name   TEXT NOT NULL,
      customer_phone  TEXT NOT NULL,
      tech_name       TEXT NOT NULL,
      amount          INTEGER NOT NULL,          -- whole dollars, as given
      status          TEXT NOT NULL CHECK (status IN ('open', 'accepted',
  'dismissed')),
      created_at      TEXT NOT NULL,
      last_contact_at TEXT                       -- snapshot value; may
  disagree with events
  );

  -- Cooldown is per customer, and one phone can have several quotes.
  CREATE INDEX IF NOT EXISTS quotes_phone ON quotes (customer_phone);

  -- Append-only event log. Primary key on event_id makes re-ingesting a
  duplicate a no-op.
  -- No CHECK on type and no foreign key on quote_id: unknown types and events
  for
  -- not-yet-imported quotes are kept, not dropped. Order comes from timestamp,
  never rowid.
  CREATE TABLE IF NOT EXISTS events (
      event_id    TEXT PRIMARY KEY,
      type        TEXT NOT NULL,
      quote_id    TEXT NOT NULL,
      timestamp   TEXT NOT NULL,
      channel     TEXT,
      direction   TEXT,
      source      TEXT NOT NULL DEFAULT 'webhook' CHECK (source IN ('webhook',
  'engine')),
      raw         TEXT NOT NULL,                 -- original JSON, for audit
  and replay
      ingested_at TEXT NOT NULL
  );

  CREATE INDEX IF NOT EXISTS events_quote_ts ON events (quote_id, timestamp);

  -- Messages the engine drafts and sends. Lifecycle:
  --   draft -> approved -> sending -> sent
  --                           \-> failed -> (retry) sending
  -- A draft can also be discarded (deleted) before approval.
  CREATE TABLE IF NOT EXISTS outbox (
      id                  INTEGER PRIMARY KEY,
      idempotency_key     TEXT NOT NULL UNIQUE,  -- re-running the engine can't
  create a second row
      quote_id            TEXT NOT NULL REFERENCES quotes (id),
      customer_phone      TEXT NOT NULL,         -- copied at draft time;
  cooldown keys on this
      channel             TEXT NOT NULL DEFAULT 'sms',
      reason              TEXT NOT NULL,
      body                TEXT NOT NULL,
      status              TEXT NOT NULL CHECK (status IN ('draft', 'approved',
  'sending', 'sent', 'failed')),
      created_at          TEXT NOT NULL,
      approved_at         TEXT,
      approved_by         TEXT,
      sent_at             TEXT,
      attempts            INTEGER NOT NULL DEFAULT 0,
      last_error          TEXT,
      provider_message_id TEXT                   -- id returned by the SMS
  provider
  );

  -- At most one in-flight message per customer at a time, enforced by the
  database
  -- rather than only by application code.

  import sqlite3
  import sys
  from pathlib import Path

  SCHEMA = Path(__file__).with_name("schema.sql")
  DEFAULT_DB = Path(__file__).resolve().parent.parent / "followup.db"


  def connect(path=DEFAULT_DB):
      conn = sqlite3.connect(path)
      conn.row_factory = sqlite3.Row
      conn.execute("PRAGMA foreign_keys = ON")
      return conn


  def init_db(conn):
      conn.executescript(SCHEMA.read_text())


  if __name__ == "__main__":
      path = sys.argv[1] if len(sys.argv) > 1 else DEFAULT_DB
      with connect(path) as conn:
          init_db(conn)
          tables = [r[0] for r in conn.execute("SELECT name FROM sqlite_master
  WHERE type = 'table'")]
      print(f"initialized {path}: {', '.join(tables)}")

⏺ Here's what I'd settle before writing the ingest code. Most of it follows from
  the data problems we found earlier.

  1. Ingest only stores; it doesn't work out state

  - Rule: ingest writes rows and never computes quote state. Status, real last
    contact and unanswered replies are all calculated afterwards, from
    timestamps.
  - Why it matters: out-of-order and late events then stop being a problem. A
    late event is just another row, and the next calculation picks it up.
  - The alternative: updating quote state as each event arrives is exactly what
    breaks when events come out of order.

  2. Running ingest twice must change nothing

  - Events: INSERT OR IGNORE on event_id. That handles the 6 duplicates and
    repeated runs.
  - Same event_id, different content: the seed doesn't have this, but real
    webhooks can. I recommend keeping the first copy and counting it as a
    conflict in the report. We shouldn't overwrite silently, and one bad event
    shouldn't fail the whole import.
  - Quotes: should importing quotes.json again overwrite existing rows or skip
    them? I recommend overwrite, because the quotes file is a snapshot from the
    quoting system, and the newest snapshot should win.

  3. Check each line, and skip bad ones without stopping

  - Reject a line if: it isn't valid JSON, it's missing event_id, type, quote_id
    or timestamp, or its timestamp can't be parsed.
  - Keep going: log the line number and continue. One bad webhook shouldn't
    block the rest of the file.
  - Store anyway: event types we don't recognise (quote_sent) and quote ids we
    haven't seen yet. The schema already allows both.

  4. Make timestamps and phone numbers consistent on the way in

  - Timestamps: convert every one to YYYY-MM-DDTHH:MM:SSZ in UTC. The schema
    relies on sorting timestamp text, so a single +00:00 or .123Z would quietly
    put events in the wrong order. The seed is already clean, but real webhooks
    won't be.
  - Phone numbers: convert to the +1XXXXXXXXXX format. The cooldown is per
    phone, so (917) 555-2003 and +19175552003 need to count as the same
    customer.

  5. One insert function for every event

  - Webhook events and the engine's own message_sent writes use the same
    function. The only difference is source='webhook' versus source='engine'.
  - Engine events get a predictable event_id, e.g. engine:<idempotency_key>.
    Retrying a send then can't write a second event either.

  6. Keep the stored data as it arrived

  - Don't create events from the snapshot's last_contact_at. Keep it on the
    quote and take the later of it and the events when calculating. The event
    log should hold only things that actually arrived.
  - Treat message_sent events already in the seed as real outbound messages.
    They count toward the cooldown even though our engine didn't send them.

  7. Mechanics

  - Load quotes before events. The outbox needs quotes to exist; events don't.
  - One transaction per file. We only skip individual bad lines, so the
    transaction doesn't have to roll back.
  - Print a short report with counts: read, inserted, duplicate, conflicting,
    rejected and unknown type. That shows the messiness was handled.

⏺ 1. The same event id arrives twice with different content

  Normally a repeated event_id is the same webhook delivered twice, which is
  what the 6 seed duplicates are. The other case is rarer: a sender bug, or a
  system reusing ids, produces the same id with different content. For example:

  {"event_id": "abc", "type": "quote_viewed",   "quote_id": "Q-1012", ...}   ←
  arrives first
  {"event_id": "abc", "type": "quote_accepted", "quote_id": "Q-1012", ...}   ←
  arrives later

  At most one of these is true, and we can't tell which. The options:

  ┌─────────────────────┬───────────────────────────────────────────────────┐
  │       Option        │                      Problem                      │
  ├─────────────────────┼───────────────────────────────────────────────────┤
  │ Keep the first,     │ In this example we'd miss the acceptance and      │
  │ report the conflict │ could message someone who already accepted.       │
  ├─────────────────────┼───────────────────────────────────────────────────┤
  │ Keep the latest     │ Events arrive out of order, so "arrived last"     │
  │ (overwrite)         │ doesn't mean "most correct". It also lets any bad │
  │                     │  webhook rewrite history.                         │
  ├─────────────────────┼───────────────────────────────────────────────────┤
  │ Fail the whole      │ One bad event blocks every good one.              │
  │ import              │                                                   │
  └─────────────────────┴───────────────────────────────────────────────────┘

  Every option is wrong some of the time, so the useful part is that the
  conflict gets reported and a person looks at it. I still recommend keep the
  first and report it. The stored data never changes underneath us, and the
  send-time guardrail check gives a second chance to catch a closed quote. A
  cheap addition would be saving the conflicting copy to a small event_conflicts
  table, so the reviewer can see both versions instead of only a count.

  2. quotes.json is imported again with different values

  Imagine tomorrow's export of quotes.json shows Q-1005 as dismissed, or has a
  corrected phone number.

  - Skip existing quotes: we'd keep the old "open" status. The event stream has
    no dismissal event type, so this snapshot is the only way we learn about a
    dismissal. Skipping means messaging a quote that was dismissed, which breaks
    one of the three guardrails. That rules out skipping.
  - Overwrite completely: this picks up dismissals and corrections, but an old
    or out-of-order export could move an accepted quote back to "open" and make
    it eligible for messages again.

  My recommendation is overwrite, with two exceptions:
  - A closed status never reopens. If the stored status is accepted or
    dismissed, an incoming "open" doesn't replace it. A real reopen is rare, a
    person can handle it by hand, and wrongly messaging a customer is worse.
  - last_contact_at keeps the later value. An older export can't move it
    backwards.

  Everything else, including name, phone, amount and tech, takes the newest
  value.

  the optional event_conflicts table if you want it.

❯ What are the key considerations involved in send flow and gaurdrails?

⏺ The plan below follows from the schema we already have and from how the policy
  works.

  1. A strict state machine

  draft ──approve──▶ approved ──claim──▶ sending ──ok──▶ sent
    │                    │                  └──error──▶ failed ──retry──▶
  sending
    └──────discard / blocked by guardrail──────▶ cancelled
  - Each step updates a row only if it's in the expected status, e.g. UPDATE …
    SET status='sending' WHERE id=? AND status='approved'. If no row changed,
    someone else got there first. That covers double-clicks and two workers
    racing for the same row.
  - I'd add a cancelled status to the schema. Without it, a draft blocked at
    send time stays in the active set. Because of the one-message-per-phone
    index, it would block that customer forever. Deleting the row instead would
    lose the record of what happened.
  - Text can be edited only while it's a draft. Approval locks the text the
    person actually approved.

  2. What the idempotency key means

  The key decides what counts as "the same follow-up", and both obvious choices
  are wrong:
  - Including the time of the run: every re-run makes a new draft.
  - Using only quote_id: we can never follow up on that quote a second time.

  Recommendation: quote_id plus the last outbound contact, e.g.
  Q-1012:after:2026-08-07T01:00:00Z.
  - Re-running on the same state gives the same key, and INSERT OR IGNORE skips
    it.
  - Once we send, the last outbound time changes, so the next quiet period can
    have its own follow-up.
  - A side effect: a draft the person discarded also blocks redrafting until
    there's new contact. I think that's correct, because the person already said
    no.

  3. Check the guardrails at send time, not only when drafting

  A lot can happen between drafting and sending: the customer accepts, or a tech
  texts them by hand. So immediately before calling the provider, the state is
  recalculated, and the send is blocked (cancelled, with the reason) if:
  - the quote is closed
  - the phone had an outbound message within the cooldown, from any quote or any
    source
  - the row's key was already sent

  The same checks also run at approval time, so the person finds out early. The
  send-time check is the one that actually protects the customer.

  4. Crashes and retries must never double-send

  The difficult case is a crash after the provider sent the text but before we
  saved that it did. The sequence:
  1. Claim the row: approved → sending, add 1 to attempts, and save that before
     calling the provider.
  2. Call the provider with the idempotency key. Real providers that support
     idempotency keys use it to drop repeated requests.
  3. On success, in one transaction: set status sent, store provider_message_id,
     and insert the message_sent event with id engine:<key>. The cooldown logic
     picks it up automatically.
  4. On a clear failure (the provider rejected it, nothing was sent): set
     failed, and a retry is safe.
  5. On an unclear result (a timeout, or a row left in sending by a crash):
     don't retry automatically. Mark it as needing a person, who checks the
     provider and then marks it sent or failed.

  That last rule is the main judgment call: at most once beats at least once. A
  missed nudge costs little, while a duplicate text makes the shop look careless
  and can break texting rules.

  5. Which clock sends use

  The send-time checks need a "now". In the demo it's the UI's "now" picker, so
  a send on "Aug 17" checks the cooldown as of Aug 17. In production it's the
  real clock. Every function takes now as a parameter so tests can control it.

  6. The provider interface

  - A small SmsProvider interface: send(to, body, idempotency_key) →
    provider_message_id.
  - A FakeProvider for the demo and tests. It writes to a log and can be set to
    fail or time out, so the retry cases can be tested.
  - Production notes for the README:
    - Twilio-style delivery callbacks arrive as events.
    - STOP opt-outs become a hard filter.
    - Texts are sent only during quiet-hour-safe times in the customer's local
      zone.
    - Rate limits apply.

  7. Re-running the engine

  - Duplicates are skipped: "Generate drafts" relies on the key (INSERT OR
    IGNORE) and the per-phone index. Either one rejecting a row means skip, not
    crash.
  - Stale drafts are cancelled: on each run, drafts whose quote has since closed
    are cancelled with a reason, so the person doesn't approve something
    already out of date.

  Decisions for you

  1. Add a cancelled status to the outbox. I recommend yes; without it a blocked
     draft stops that customer from ever getting another message.
  2. At most once: an unclear send waits for a person instead of retrying
     automatically.
  3. The idempotency key is quote + last outbound contact.
  4. The demo uses the UI's "now" as the clock for sends.

  If you agree with all four, I'll log them in notes.md and build it.

⏺ The simplest version that still meets all three required guardrails:

  Flow

  draft ──approve──▶ approved ──send──▶ sent
    │                                └──blocked──▶ failed (with the reason)
    └──discard──▶ (deleted)
  1. Generate drafts: one button. It creates a draft from a template for each of
     today's top 10 candidates, with one template per tier.
  2. Approve: one button per draft. Records who approved it and when.
  3. Send: one button per approved draft. Inside one database transaction it:
     - checks the row is still approved
     - checks the quote isn't closed and the phone isn't in cooldown, reusing
       the policy code
     - "sends" through a fake provider that only logs
     - marks the row sent and writes the message_sent event
  4. Discard: deletes a draft.

  Why the three guardrails still hold

  ┌──────────────────┬──────────────────────────────────────────────────────┐
  │    Guardrail     │                         How                          │
  ├──────────────────┼──────────────────────────────────────────────────────┤
  │ No second        │ Checked at send time with the same per-phone logic   │
  │ message within   │ as the policy. The sent message becomes a            │
  │ the cooldown     │ message_sent event, so the next run sees it          │
  │                  │ automatically.                                       │
  ├──────────────────┼──────────────────────────────────────────────────────┤
  │ No message about │ Checked at send time. A blocked send is marked       │
  │  a closed quote  │ failed with the reason, which also frees that        │
  │                  │ customer for later messages.                         │
  ├──────────────────┼──────────────────────────────────────────────────────┤
  │ No double-send   │ Re-run: the idempotency key is quote + last outbound │
  │ on re-run or     │  contact, so a duplicate draft is skipped. Retry:    │
  │ retry            │ send only acts on approved rows, so clicking twice,  │
  │                  │ or pressing send again on a sent row, does nothing.  │
  └──────────────────┴──────────────────────────────────────────────────────┘

⏺ This lines up with the "Allow retrying a failed send" item in your
  changes_needed.md.

  Re-running the engine is already safe. The unique idempotency key, the
  one-message-per-phone index and the rule that customers with a message waiting
  aren't candidates together stop a second row from being created. Retry is the
  gap. A failed row is currently final, so the guarantee holds only because
  retrying isn't possible.

  The simplest approach that still works: three small pieces

  1. Separate "blocked" from "failed", using the status itself.
  - blocked: a guardrail stopped it (quote closed, customer in cooldown). It
    stays final.
  - failed: the provider errored. It can be retried.

  Today both share failed and differ only by an error-message prefix. Splitting
  the status removes that string matching.

  2. A retry reuses the same row and the same send function. send() accepts rows
  that are approved or failed. A retry never creates a new row, so it carries
  the same idempotency key, the guardrails are checked again, and success is
  recorded in one transaction as now.
  - Once a row is sent, any further retry or double-click finds nothing to act
    on and does nothing.
  - The row goes straight from failed to sent without passing back through an
    active status. That avoids the per-phone index collision your notes warn
    about. If another draft for the same phone exists, whichever sends first
    puts the customer in cooldown, and the other is blocked.

  3. The fake provider honours the idempotency key. If it has already accepted a
  key, it returns the original message id without sending again. Real providers
  that support idempotency keys behave this way.

  This is the piece that makes retry fully safe. The dangerous case is a
  provider that sent the text but timed out before replying, or a crash before
  our database records the send. The retry then sends the same key again, and
  the provider drops the duplicate. That covers the crash gap without the more
  complex sending status.

  Tests (about 4)

  - The provider fails, the retry succeeds → 1 text sent, 1 message_sent event.
  - The provider sends but then raises an error (a timeout) → the retry still
    results in 1 text, because the provider drops the repeat.
  - Retrying twice after success → the second does nothing.
  - A blocked row can't be retried.

  Cost

  About 20 minutes. One catch: adding blocked changes the status rule in the
  schema, and SQLite can't change that on an existing table. The local
  takehome.db will need deleting and the seed data reloaded. That's fine here
  because the database is a gitignored dev file. In production this would be a
  migration.

  2. What the "7-day quiet period" means

  customer directly. It only changes who the engine suggests, and only for Gone
  cold quotes.

  Today: a Gone cold quote has no signal at all: no recent view, no reply, and
  under $5k. It's suggested again as soon as the 72h cooldown ends, so it gets
  nudged every 3 days, up to 3 times. That's 3 texts in about 9 days to someone

  With the change: a Gone cold quote is only suggested once 7 days have passed
  since our last outbound contact, or since the quote was sent if we've never
  contacted them.

  What starts and resets the 7 days:
  - Starts: the quote is sent, or we send any outbound message.
  - Skips it: any customer activity moves the quote to a higher tier with no
    7-day wait. A recent view makes it Hot, and a reply makes it Needs a reply.
  - Not affected: Needs a reply, Hot and Big and quiet keep their own rules (big
    quotes already wait 5 days).

  The pattern makes sense: interest or more money means a sooner follow-up, and
  no signal means waiting longer.

❯ How can I export a chat again?

⏺ In Claude Code, type the slash command /export into the chat input. It offers
  two options:
  - copy the conversation to your clipboard
  - save it to a file, e.g. /export robby-session-1.txt

  You need to export every session:
  1. In a terminal, from the project folder, run claude --resume.
  2. Pick the session from the list.
  3. Type /export <filename>.
  4. Repeat for each session.

  If /export isn't available in the VS Code extension's chat, which I'm not
  certain about, the claude --resume route above works from the terminal. Claude
  Code also keeps the raw transcripts as .jsonl files in
  ~/.claude/projects/-Users-charlieheus-Desktop-Robby/, one file per session, if
  you'd rather submit those directly.

  Do this last, after your final README edit, so the export includes everything.
